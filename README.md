# hh-vacancies-analyzer

Два инструмента:
1. **`hh_vacancies.py`** — CLI-скрапер: собирает вакансии и сохраняет в JSON + CSV.
2. **`bot.py`** — Telegram-бот: в фоне собирает вакансии, анализирует требования
   через LLM (со словарным резервным режимом) и показывает топ, тренды и дифф.

## Архитектура бота

| Модуль | Роль |
|---|---|
| `hh_vacancies.py` | скрапер + авторизация (`build_session`, `fetch_vacancies`) |
| `skills_dict.py` | словарь технологий: синоним→канон, неоднозначные, спецсимвольные |
| `extract.py` | извлечение: gazetteer по `description`+`key_skills`, DF, co-occurrence |
| `storage.py` | SQLite: снимки, счётчики, детали вакансий, пользователи, квоты |
| `jobs.py` | очередь задач: постановка с дедупом, выдача воркерам, подписки |
| `collector.py` | один прогон сбора: N свежих → детали → извлечение → запись |
| `analysis.py` | текущий топ, тренд за период, дифф с прошлого сбора |
| `bot.py` | python-telegram-bot: inline-кнопки, воркеры очереди, JobQueue |

## Многопользовательский режим

Бот рассчитан на 100–200 пользователей в личке на одном процессе и SQLite.

**Доступ — по инвайт-коду.** Админ (`TELEGRAM_ADMIN_CHATS`) выдаёт код командой
`/invite [использований] [заметка]`; новый пользователь присылает его в ответ на
`/start`. Учёт — в таблице `users`, управление: `/users`, `/ban`, `/unban`, `/stats`.

**Очередь вместо отказов.** Сборы не выполняются в обработчике — они ставятся в
таблицу `jobs`. Одинаковые `(запрос, регион, режим)` схлопываются в одну задачу, а
пользователи становятся её подписчиками: десять человек, спросивших `golang`,
получают один сбор и все — результат. Пользователю никогда не отвечают «занято»:
есть устаревший снимок — он показывается сразу, а свежий досылается.

Задачи выполняют `WORKERS` воркеров. Сеть к hh идёт под семафором `HH_CONCURRENCY=1`
(общий токен и один IP — параллелить нельзя), анализ LLM — под `LLM_CONCURRENCY`.
Пока одна задача считается моделью, другая качает вакансии. Задачи, оставшиеся
`running` после падения процесса, возвращаются в очередь при старте.

**Квоты на LLM.** `LLM_DAILY_QUOTA_USER` анализов в сутки на пользователя; сверх —
отказ. `LLM_DAILY_QUOTA_GLOBAL` — общий предохранитель бюджета: при его исчерпании
не отказываем, а считаем по словарю. Подписка на чужую уже идущую задачу квоту не
тратит.

**Сохранённые фильтры и отслеживание.** Поисковый запрос и регион сохраняются
в «Фильтрах» как пара; её можно снова выбрать одной кнопкой. `/track` включает
автосбор выбранной пары (до `TRACK_LIMIT_USER` на человека, до
`TRACKED_MAX_TOTAL` уникальных пар всего). Каждая отслеживаемая пара собирается
примерно раз в `COLLECT_HOURS` через LLM; новые детали загружаются из hh.ru,
известные берутся из кэша, анализируется весь снимок. При изменении топ-15
требований подписчикам отправляется дифф; первый снимок служит исходной точкой.
Одинаковые пары разных пользователей собираются один раз. `/untrack` прекращает
автосбор и уведомления, но оставляет фильтр и историю.
«➕ Новый запрос» всегда создаёт отдельный фильтр, карандаш исправляет текст
выбранного сохранённого фильтра. Кнопки региона меняют его регион без создания
дубликата; включённое отслеживание переносится на новую пару, а старые снимки
остаются привязаны к прежней паре. Кнопка `python` выбирает уже сохранённую
пару `python` вместе с её регионом; затем регион можно поменять верхней кнопкой.

**Хранение.** Детали вакансии лежат в `vacancy_details` один раз, снимок ссылается
на них через `snapshot_items` — иначе одна и та же вакансия копировалась бы в
десятки снимков (на реальной базе это дало сокращение 17 → 7 МБ). Сырьё разовых
запросов живёт `RETENTION_ADHOC_DAYS`, отслеживаемых — `RETENTION_RAW_DAYS`.

Сырьё отслеживаемых запросов хранится 30 дней, разовых — 7 дней. Снимки, топы,
связанные агрегаты и завершённые задачи удаляются через 180 дней; настройки,
пользователи и сохранённые фильтры остаются. Очистка выполняется после сбора и
ежедневно, затем SQLite освобождает место через `VACUUM`. Резервные копии БД,
созданные при деплоях с именем `hh_stats.db.pre-*`, также удаляются через 180 дней.

БД со старой схемой мигрирует при первом запуске автоматически; прежняя таблица
сохраняется как `vacancies_old` — удалите её вручную, убедившись, что всё на месте.

### Тесты

```bash
.venv/bin/python -m pytest test_multiuser.py -q
```

**Как извлекаются технологии (без LLM):** для N самых свежих вакансий тянется деталь
`GET /vacancies/{id}` — из неё берутся структурные `key_skills` и полный `description`.
По ним работает gazetteer-матчинг (словарь технологий с синонимами и обработкой
`C++`/`C#`/`Node.js`), метрика — document frequency (в скольких вакансиях встречается
технология). Тренды считаются сравнением снимков во времени. Поиск `/vacancies` сам
`key_skills` не отдаёт — потому и нужна деталь по каждой вакансии.

## Скрапер (`hh_vacancies.py`)

Собирает вакансии с hh.ru через API поиска и сохраняет в JSON + CSV.

## Зачем нужен токен

Поиск `/vacancies` формально публичный, но анти-бот hh отдаёт **403** на запросы
с хостинговых/облачных IP **без авторизации** (проверено — с текущего IP `/areas`
отвечает 200, а `/vacancies` — 403). Авторизация токеном приложения снимает блок.

Токен приложения берётся автоматически по `grant_type=client_credentials` —
вход пользователя не нужен, достаточно `client_id` и `client_secret`.

## Настройка

1. Возьми `client_id` и `client_secret` своего приложения на https://dev.hh.ru/admin
2. Скопируй `.env.example` → `.env` и заполни их (или экспортируй в окружение).

## Запуск

```bash
export HH_CLIENT_ID=...      # либо `set -a; source .env; set +a`
export HH_CLIENT_SECRET=...

# python-вакансии по России, до 500 штук
python3 hh_vacancies.py

# свой запрос и регион (113=Россия, all=без ограничения), собрать всё доступное
python3 hh_vacancies.py --text "python developer" --area all --max-items 0
```

Параметры: `--text`, `--area`, `--per-page` (макс 100), `--max-items` (0 = всё,
но hh отдаёт максимум 2000 на один запрос), `--out-dir`.

## Выход

`vacancies_<text>_<timestamp>.json` (сырой ответ hh) и `.csv` (плоская таблица:
название, компания, регион, вилка, опыт, график, ссылка).

## Telegram-бот (`bot.py`)

### Установка зависимостей

```bash
uv venv .venv
uv pip install --python .venv -r requirements.txt
```

### Запуск

```bash
export TELEGRAM_BOT_TOKEN="123:ABC..."   # от @BotFather (или token.txt рядом со скриптом)
export HH_CLIENT_ID=... HH_CLIENT_SECRET=...   # приложение hh — для токена (снимает 403)
.venv/bin/python bot.py
```

Все параметры — в `.env.example` (интервал сбора, регион, размер выборки, число
воркеров, квоты, лимиты подписок); есть разумные дефолты. Свой запрос из кнопки
«✏️ свой запрос» сохраняет фильтр; чтобы по нему шёл автосбор и приходили
уведомления об изменении топа — `/track`.

### Кнопки

- **📊 Топ требований** — самые частые технологии в текущем снимке (доля вакансий);
- **📈 Тренд за месяц** — что выросло/упало/появилось/исчезло за период;
- **🔁 Что изменилось** — дифф с прошлого сбора;
- **⚙️ Фильтры** — регион «Весь мир» (все регионы вакансий hh.ru) или Россия,
  период, размер топа, сохранённые запросы, 📌 отслеживание;
- **⟳ Загрузить свежие** — поставить сбор в очередь.

Команды: `/top /vacancies /trend /diff /filters /status /track /untrack /tracked /help`;
для админа (`TELEGRAM_ADMIN_CHATS`) — `/invite`, `/users`, `/ban`, `/unban`, `/stats`,
`/collect` (форс-сбор) и `/dict` (кандидаты в словарь технологий).

### Про 403

Если hh отдаёт **403** на сборе (облачный IP без токена), бот пишет об этом в `/status`
и в ответ на `📊 Топ требований`. Решение — задать `HH_CLIENT_ID`/`HH_CLIENT_SECRET`
или запускать с домашнего IP.
